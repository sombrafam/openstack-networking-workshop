## 2. Background & Concepts

### 2.1 Why OVN?

In Lab 4, we manually programmed OVS flows and namespace-based routing to
implement forwarding and connectivity. This works for a few ports but doesn't
scale — in a real cloud with thousands of VMs, you need **automation**.

**OVN (Open Virtual Network)** is the SDN controller built on top of OVS. It:
- Accepts high-level intent ("create a network", "add a router").
- Compiles intent into **logical flows**.
- Distributes logical flows to every host.
- Each host's `ovn-controller` translates logical flows into **physical OVS
  OpenFlow rules**.

No iptables. No router namespaces. No manual `sysctl`. OVN handles all of
it in OVS flows.

**This lab is a hand-over, not a rebuild.** You keep the exact same `br-int`,
the same veth pairs, and the same `ns-a`/`ns-b`/`ns-c` namespaces from Labs 3
and 4. Nothing in the data plane is torn down. The only change is *who
programs the flow table*: until now it was you, typing `ovs-ofctl add-flow`;
from here on it is `ovn-controller`. Watching the same topology keep working
while its control plane is replaced underneath is the point of the lab.

### 2.2 OVN Architecture

```
                     ┌───────────────────────────┐
                     │      Northbound DB        │  ← Logical topology
                     │ (networks, routers, ACLs) │     (what Neutron writes to)
                     └─────────────┬─────────────┘
                                   │
                     ┌─────────────▼─────────────┐
                     │        ovn-northd         │  ← Compiles NB → SB
                     └─────────────┬─────────────┘
                                   │
                     ┌─────────────▼─────────────┐
                     │      Southbound DB        │  ← Physical bindings +
                     │ (logical flows, chassis)  │     compiled flows
                     └──────┬─────────────┬──────┘
                            │             │
              ┌─────────────▼──┐   ┌──────▼───────────┐
              │ ovn-controller │   │  ovn-controller  │
              │   (Host A)     │   │    (Host B)      │
              └───────┬────────┘   └───────┬──────────┘
                      │                    │
              ┌───────▼────────┐   ┌───────▼───────────┐
              │  OVS br-int    │   │   OVS br-int      │
              │  (Host A)      │   │   (Host B)        │
              └────────────────┘   └───────────────────┘
```

### 2.3 Key OVN Concepts

| OVN Concept | OpenStack Equivalent | Description | Covered in |
|-------------|---------------------|-------------|------------|
| Logical Switch | Neutron Network | A virtual L2 network | **Lab 5**  |
| Logical Switch Port | Neutron Port | A virtual NIC on a network | **Lab 5**  |
| Chassis | Compute/Network Node | A physical host running ovn-controller | **Lab 5**  |
| Logical Router | Neutron Router | A virtual L3 router | Lab 6      |
| Logical Router Port | Router interface | Connects a router to a switch | Lab 6      |
| ACL | Security Group Rule | Allow/deny rules on a port | Lab 6      |
| DHCP Options | Subnet DHCP settings | DHCP server configuration | Lab 6      |

### 2.4 Logical Flows vs. OpenFlow Flows

OVN operates at two levels:

1. **Logical flows** (`ovn-sbctl lflow-list`): Express intent in terms of
   logical ports and switches — **location-independent**.

2. **OpenFlow flows** (`ovs-ofctl dump-flows br-int`): The physical
   realization on a specific host. `ovn-controller` generates these by
   combining logical flows with local binding information.

### 2.5 Geneve Tunnels

OVN uses **Geneve** as its overlay protocol. Unlike VXLAN, Geneve supports
extensible TLV headers — OVN uses these to carry logical datapath and port
metadata. OVN automatically manages tunnel creation between all chassis.

Contrast this with Lab 4, where you created the VXLAN tunnel by hand on both
ends: with OVN you never run an `add-port` for a tunnel again. This lab has
only one chassis, so no tunnel is built at all — but the encapsulation type is
still declared during chassis registration, and the moment a second chassis
appears OVN would mesh them automatically.

## 3. Architecture Diagram

**Starting point — the end-state of Lab 4 (Host A):**

```
   ns-a            ns-b            ns-c
   veth-a          veth-b          veth-c
   .10             .20             .30
     │               │               │

 ┌──────────────── OVN Central (this host) ────────────────────────┐

 │                            br-int                               │
 │    veth-a-ovs          veth-b-ovs          veth-c-ovs           │

 │    ls1-port-a          ls1-port-b          ls1-port-c           │
 └─────────┬───────────────────┬───────────────────┬───────────────┘
           │                   │                   │
      ┌────▼─────┐        ┌────▼─────┐        ┌────▼─────┐
      │   ns-a   │        │   ns-b   │        │   ns-c   │
      │  veth-a  │        │  veth-b  │        │  veth-c  │
      │   .10    │        │   .20    │        │   .30    │
      └──────────┘        └──────────┘        └──────────┘

   Logical view :  ls1 — one logical switch, three logical ports
   Physical view:  br-int — the identical bridge from Lab 3
   Subnet       :  192.168.100.0/24 — unchanged since Lab 2
```

The namespaces, the veth pairs, the bridge, and the addresses are all
untouched. What changes is the contents of `br-int`'s flow table.

### Addressing

| Namespace | Interface | MAC | IP | Logical port |
|-----------|-----------|-----|----|--------------|
| `ns-a` | `veth-a` | `aa:bb:cc:00:00:01` | 192.168.100.10/24 | `ls1-port-a` |
| `ns-b` | `veth-b` | `aa:bb:cc:00:00:02` | 192.168.100.20/24 | `ls1-port-b` |
| `ns-c` | `veth-c` | `aa:bb:cc:00:00:03` | 192.168.100.30/24 | `ls1-port-c` |

The IP addresses are the ones you have used since Lab 2. The MAC addresses
are new: veth pairs get random MACs at creation, and OVN needs to know each
port's address in order to build its ARP responder and enforce port security.
Rather than reading the random values, you will **pin** them — which is also
what a cloud does, since Neutron allocates the MAC first and Nova then
configures the VM's NIC to match.

### Exercise 4 — Bind the Logical Ports to the Existing Interfaces

This is the step that connects the logical world to the physical one. The
veth interfaces are already on `br-int` — you only need to tell OVS which
logical port each one represents.

```bash
sudo ovs-vsctl set interface veth-a-ovs external-ids:iface-id=ls1-port-a
sudo ovs-vsctl set interface veth-b-ovs external-ids:iface-id=ls1-port-b
sudo ovs-vsctl set interface veth-c-ovs external-ids:iface-id=ls1-port-c
```

**Verify:**
- `ovn-sbctl show` now shows all three ports as **bound** to the local
  chassis.
- `ovn-nbctl show` reports the ports `up`.
- Ping between all three namespaces — L2 connectivity, now via OVN.

```bash
sudo ip netns exec ns-a ping -c2 192.168.100.20
sudo ip netns exec ns-a ping -c2 192.168.100.30
sudo ip netns exec ns-b ping -c2 192.168.100.30
```

### Exercise 5 — Understanding OVN and OVS Flows

You now have the same connectivity you had at the end of Lab 3 — but the
mechanism underneath is completely different. The goal of this exercise is to
learn to **read** both levels, so that a flow dump stops being noise.

Dump each level side by side:

```bash
# Logical: location-independent intent
sudo ovn-sbctl lflow-list ls1

# Physical: what this chassis actually installed
sudo ovs-ofctl dump-flows br-int
```

#### 5.1 Anatomy of a logical flow

A line from `lflow-list` looks like this:

```
Datapath: "ls1" (a1b2c3d4-…)  Pipeline: ingress
  table=25 (ls_in_l2_lkup), priority=50,
    match=(eth.dst == aa:bb:cc:00:00:02), action=(outport = "ls1-port-b"; output;)
```

| Field | Meaning |
|---|---|
| `Datapath` | Which logical switch or router this flow belongs to |
| `Pipeline` | `ingress` = packet leaving a port · `egress` = packet arriving at one |
| `table=N (name)` | The pipeline **stage**. Read the *name* — numbers shift between OVN versions |
| `priority` | Highest match wins, exactly like OpenFlow |
| `match` | OVN's own expression language — `&&`, `==`, named ports |
| `action` | OVN actions: `next;`, `drop;`, `output;`, `outport = "…";` |

> The match/action syntax here is **not** OpenFlow. It is a higher-level
> language that `ovn-northd` emits and `ovn-controller` compiles.

List the stage names in pipeline order — they are effectively a table of
contents for everything OVN can do:

```bash
sudo ovn-sbctl lflow-list ls1 | grep -oP 'table=\s*\d+\s*\(\K[a-z_]+' | uniq
```

#### 5.2 Anatomy of an OpenFlow rule

The same intent, compiled for this host:

```
cookie=0x5b8f2e11, duration=812.443s, table=8, n_packets=14, n_bytes=1372,
  priority=50,reg14=0x1,metadata=0x1,dl_src=aa:bb:cc:00:00:01 actions=resubmit(,9)
```

| Field | Meaning |
|---|---|
| `cookie` | Fingerprint of the logical flow that generated this rule |
| `duration` | How long the rule has been installed |
| `table=N` | Physical table — a compiled pipeline stage |
| `n_packets` / `n_bytes` | Hit counters. **The single most useful debugging signal** |
| `match` | Real OpenFlow fields (`reg14`, `metadata`, `dl_src`, …) |
| `actions` | Usually `resubmit(,N)` — the pipeline is a table walk, not one lookup |

#### 5.3 How one becomes the other

`ovn-controller` has to encode logical identity into OpenFlow match fields:

| Logical concept | Becomes | Example |
|---|---|---|
| Logical datapath (`ls1`) | `metadata` | `metadata=0x1` |
| Ingress port (`inport`) | `reg14` | `reg14=0x1` |
| Egress port (`outport`) | `reg15` | `reg15=0x2` |
| Pipeline stage | `table=N` | `table=8` |
| Logical flow identity | `cookie` | `cookie=0x5b8f2e11` |

Find your own values and then locate the matching rules:

```bash
# The datapath tunnel key for ls1 -> this is the metadata value
sudo ovn-sbctl get Datapath_Binding ls1 tunnel_key

# The logical port numbers -> these are reg14 / reg15 values
sudo ovn-sbctl list Port_Binding | grep -E 'logical_port|tunnel_key'

# Now grep the physical table for one logical switch
sudo ovs-ofctl dump-flows br-int | grep 'metadata=0x1'
```

Map compiled rules back to the logical flows that produced them:

```bash
sudo ovs-ofctl dump-flows br-int | ovn-detrace
```

**Questions:**

## 5. Key Commands Reference

**Logical topology (Northbound)**

| Command | Description |
|---------|-------------|
| `ovn-nbctl ls-add <name>` | Create a logical switch |
| `ovn-nbctl ls-del <name>` | Delete a logical switch |
| `ovn-nbctl lsp-add <switch> <port>` | Add a port to a switch |
| `ovn-nbctl lsp-set-addresses <port> "<mac> <ip>"` | Set port addresses |
| `ovn-nbctl lsp-set-port-security <port> "<mac> <ip>"` | Enable port security |
| `ovn-nbctl show` | Show the logical topology |

**Bindings and physical state (Southbound)**

| Command | Description |
|---------|-------------|
| `ovs-vsctl set interface <if> external-ids:iface-id=<lsp>` | Bind an OVS interface to a logical port |
| `ovs-vsctl set open . external-ids:ovn-remote=<target>` | Point the chassis at the Southbound DB |
| `ovn-sbctl show` | Show chassis and port bindings |
| `ovn-sbctl list Port_Binding <port>` | Inspect one binding in detail |

**Reading the flows**

| Command | Description |
|---------|-------------|
| `ovn-sbctl lflow-list [<datapath>]` | List logical flows |
| `ovs-ofctl dump-flows <bridge>` | List the compiled OpenFlow rules |
| `ovs-ofctl dump-flows <bridge> \| ovn-detrace` | Annotate OpenFlow rules with their logical flow |
| `ovn-sbctl get Datapath_Binding <ls> tunnel_key` | The `metadata` value for a logical switch |
| `ovn-sbctl list Port_Binding` | Port tunnel keys — the `reg14` / `reg15` values |
