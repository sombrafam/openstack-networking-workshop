OpenStack Networking Workshop

Build a complete OpenStack-style virtual network from first principles — namespaces, veth pairs, Open vSwitch, OpenFlow, and finally OVN.

This workshop walks you, hands-on, through the same data-plane primitives OpenStack Neutron uses under the hood. Nine labs, roughly 10.5 hours end to end. Labs 1–5 need nothing but this page — they run in the embedded mock lab environment. Labs 6–9 step up to a real Linux host, a second node, and finally a live OpenStack cloud.

The nine labs

Lab 1 · ~45 minTAP devices & namespaces

Isolation primitives: virtual NICs and per-process network stacks.

 Lab 2 · ~45 minVeth pairs

Connect two namespaces and watch ARP fly across the wire.

 Lab 3 · ~1 hrOVS as an L2 switch

Three namespaces, one virtual switch, MAC learning in action.

 Lab 4 · ~1.5 hrOpenFlow rules & tunnels

Program OVS by hand. Drop traffic with a flow. Meet VXLAN and Geneve.

 Lab 5 · ~2.5 hrOVN basics

Logical switches, routers, ACLs, native DHCP. Map it all to Neutron.

 Lab 6 · ~1.5 hrNative services & security groups

DHCP, IPAM, DNS, metadata, port groups and stateful ACLs.

 Lab 7 · ~1 hrMulti-node OVN

Two hosts, one logical switch, Geneve tunnels in between.

 Lab 8 · ~45 minMulti-chassis, DVR & FIPs

Distributed routing, gateway HA with BFD, floating IPs.

 Lab 9 · ~45 minNeutron ML2/OVN

Capstone: watch OpenStack write the OVN database you built by hand.

What you will learn

  • How Linux network namespaces, veth pairs, and TAP devices isolate and connect virtual NICs.
  • How Open vSwitch differs from a Linux bridge, and why OVN sits on top of OVS.
  • How OpenFlow rules are matched, prioritised, and chained across tables.
  • How VXLAN encapsulates Layer 2 over a routed underlay — and why OVN prefers Geneve.
  • How every OVN concept (logical switch, router, ACL, DHCP options) maps onto Neutron CLI calls.
  • How OVN serves DHCP, DNS, and instance metadata without a single daemon on a network node.
  • How OpenStack security groups are modelled as port groups, address sets, and stateful ACLs.
  • How distributed routing, gateway HA, and floating IPs actually behave across multiple chassis.
  • How Neutron’s ML2/OVN driver turns an API call into an OpenFlow rule on a compute node.

Recommended path

  1. Read Getting started for prerequisites and environment options.
  2. Skim the Lab environment page to learn the embedded terminal.
  3. Work through Labs 1–5 in order — each builds on the previous, and all of them run in the embedded terminal.
  4. For Labs 6–9, provision a real Linux host (and a second node from Lab 7 on). See Getting started.
  5. Keep the Command reference open in another tab.

Workshop›Getting started

Getting started

This workshop is hands-on. You will run ip netns, ovs-vsctl, ovn-nbctl and friends. You can do that in three different environments — pick whichever suits you.

Prerequisites

  • Comfort with the Linux command line.
  • Basic networking: IP addresses, subnets, MAC addresses, ARP, ICMP.
  • For the real-host options: a recent Ubuntu (22.04 or newer) and sudo rights.

Option 1: The mock lab environment (recommended)

The fastest way to start. Every lab page embeds an interactive terminal that simulates the commands you would run on a real host. No VM, no installs, no risk of breaking your laptop.

Open any lab and start typing. The terminal seeds the state from the previous lab so you can pick up where you left off.

Best for

Reading and learning — you can complete every exercise this way.

Option 2: A single Linux VM

If you want the real thing, the simplest setup is a single Ubuntu VM with everything installed locally:

apt update
apt install -y iproute2 openvswitch-switch ovn-central ovn-host tcpdump

Every command in every lab works on this single host. The chassis IP and tunnel endpoint are simply 127.0.0.1.

Option 3: A multi-node setup

For the full distributed experience — Geneve tunnels between real chassis — you need two or more Linux hosts. See the Reference, section Multi-node setup guidance, for the broad strokes.

Privileges and cleanup

Every command in this workshop requires root or sudo. The mock environment runs as root. On real hosts, prefix with sudo.

Each lab ends with a cleanup step. If you skip it you can always wipe namespaces and the bridge by hand:

for ns in $(ip netns list | awk '{print $1}'); do ip netns del $ns; done
ovs-vsctl del-br br-int 2>/dev/null || true

Lab 1 — TAP devices & namespaces

Tier
Fundamentals
Duration
~45 minutes
Prerequisites
Comfort with the Linux CLI and basic networking.

Objectives

  • Understand what a network namespace is and why OpenStack uses them.
  • Create, list and delete namespaces.
  • Create a TAP device and place it inside a namespace.
  • Verify isolation: namespaces have independent interfaces, addresses and routes.

Background

A network namespace gives a process its own private network stack: its own interfaces, its own ARP table, its own routes. Two namespaces cannot see each other’s traffic unless you explicitly connect them. This is the same isolation primitive containers use.

A TAP device is a virtual Layer 2 NIC. The kernel treats it as a real Ethernet interface; a userspace program (or, in OpenStack, QEMU) can read and write Ethernet frames through it. Every VM in OpenStack has a TAP device on the hypervisor.

Background

A veth pair is a kernel construct: two virtual Ethernet interfaces wired together back-to-back. Whatever you transmit on one end appears on the other. They are the standard way to connect a namespace (or container) to another namespace or to a bridge.

Lab 3 — OVS as an L2 switch

Tier
Open vSwitch
Duration
~1 hour
Prerequisites

Objectives

  • Explain why OpenStack uses OVS rather than the Linux bridge.
  • Create an OVS bridge and connect three namespaces through it.

Why a virtual switch?

In Lab 2 you connected two namespaces with one veth pair. For three or more, a full mesh scales as O(N²). A switch reduces that to O(N): each namespace gets one veth, the other end plugs into the switch.

Full mesh (3 namespaces): Star via switch: ns-a ──── ns-b ns-a ─┐ \ / ns-b ─┼── br-int (OVS) ns-c ns-c ─┘ (3 pairs, O(N²)) (3 pairs, O(N))

Why OVS, not the Linux bridge?

FeatureLinux bridgeOVS
MAC learningYesYes
Programmable flow rulesNoYes
OpenFlow controllerNoYes
VXLAN / Geneve tunnelsNoYes
Used by OVNNoYes

OpenFlow basics

A flow rule has three parts: match (in_port, MAC, IP, ports, …), priority (0–65535, higher wins), and actions (output:<port>, drop, resubmit(,N), NORMAL, …).

Incoming packet │ ▼ ┌─ Table 0 ──────────────────────────────────────────┐ │ priority=200, ip, nw_src=10.0.0.1 → actions=drop │ │ priority=100, ip → actions=NORMAL│ │ priority=0 → actions=NORMAL│ └────────────────────────────────────────────────────┘

First match by descending priority wins.

VXLAN & Geneve

VXLAN encapsulates Ethernet frames inside UDP (port 4789). Each tunnel carries a 24-bit VNI (~16M values). OVN uses Geneve instead, because Geneve’s TLV headers can carry OVN’s logical datapath and port metadata.

PropertyVXLANGeneve
HeaderFixedExtensible TLVs
OVN metadataNot supportedCarries datapath + port IDs
RFC73488926

Why OVN?

Programming OVS by hand works for a few ports. For a real cloud with thousands of VMs you need automation. OVN takes high-level intent (“create a network”), compiles it into logical flows, distributes them, and lets each chassis’ ovn-controller compile them into local OpenFlow rules.

What Lab 5 hardcoded

In Lab 5 every port got a fixed MAC and IP, typed twice — once in the namespace with ip addr add, once in OVN with lsp-set-addresses. Real clouds do not work that way: a VM boots knowing nothing, and the network tells it who it is. That handoff is DHCP, DNS, and metadata — and in OVN all three are distributed, implemented as logical flows on every chassis rather than as a daemon on a network node.

Part A — OVN-native DHCP

A DHCP_Options row is a description of a DHCP server, not a process. ovn-northd compiles it into logical flows that every chassis installs. When a VM broadcasts DISCOVER, the flow on that VM’s own hypervisor answers it. The broadcast never leaves the host, and there is no dnsmasq anywhere.

ovn-nbctl create DHCP_Options cidr=10.0.1.0/24 \
  options="\"server_id\"=\"10.0.1.1\" \"server_mac\"=\"aa:bb:cc:00:01:01\" \
           \"lease_time\"=\"3600\" \"router\"=\"10.0.1.1\" \"mtu\"=\"1442\""
OptionMeaningNeutron source
cidrSubnet this server ownssubnet.cidr
server_id / server_macIdentity in the OFFERRouter interface / subnet gateway
lease_timeLease duration in secondsML2/OVN default (86400)
routerDefault gateway pushed to the VMsubnet.gateway_ip
mtuMTU pushed to the VMpath_mtu minus Geneve overhead
dns_serverResolver listsubnet.dns_nameservers
MTU

Geneve adds roughly 58 bytes of encapsulation. Pushing 1442 instead of 1500 avoids fragmentation inside the tunnel. Neutron computes this from global_physnet_mtu and path_mtu; getting it wrong is a classic “SSH hangs after the banner” bug.

Dynamic addressing (IPAM)

lsp-set-addresses takes three forms, and they differ in who owns the address:

FormMACIPNeutron analogue
"aa:bb:cc:00:00:01 10.0.1.10"youyouPort with a fixed IP
"aa:bb:cc:00:00:01 dynamic"youOVNPort with Neutron-allocated IP
dynamicOVNOVNFully auto-allocated port
 
ovn-nbctl set Logical_Switch ls1 other_config:subnet="10.0.1.0/24"
ovn-nbctl set Logical_Switch ls1 other_config:exclude_ips="10.0.1.1..10.0.1.9"
ovn-nbctl lsp-set-addresses ls1-port1 dynamic
ovn-nbctl get Logical_Switch_Port ls1-port1 dynamic_addresses

exclude_ips is OVN’s equivalent of a Neutron subnet’s allocation pool boundary — it keeps gateway and service addresses out of the pool.

OVN DNS

The DNS table holds name→address records attached to a logical switch. ovn-northd compiles them into a dns_lookup action, so an instance’s query is answered by its own hypervisor.

DNS_UUID=$(ovn-nbctl create DNS records:web1="10.0.1.10")
ovn-nbctl add Logical_Switch ls1 dns_records $DNS_UUID

This is what Neutron calls internal DNS: dns_domain plus the port’s dns_name.

Metadata — the localport

Every cloud instance fetches user-data from 169.254.169.254. That address must exist identically on every hypervisor and must never be tunnelled. OVN’s answer is the localport: a logical port that exists on every chassis simultaneously and whose traffic is never sent over Geneve.

VM (any chassis) │ GET http://169.254.169.254/latest/meta-data/ ▼ ┌────────────────────────┐ │ br-int (this host) │ │ localport ls1-meta │ ← same port on every chassis └───────────┬────────────┘ │ never crosses a Geneve tunnel ▼ ovn-metadata-agent namespace → nova-api metadata 
ovn-nbctl lsp-add ls1 ls1-meta
ovn-nbctl lsp-set-type ls1-meta localport
ovn-nbctl lsp-set-addresses ls1-meta "aa:bb:cc:00:0f:fe 169.254.169.254"

Part B — Security groups

Lab 5’s ACLs attached to a logical switch, so every port on the network got the same policy. OpenStack needs two VMs on the same network to sit in different security groups. The OVN construct for that is the port group.

ovn-nbctl pg-add pg-web ls1-port1
ovn-nbctl pg-set-ports pg-web ls1-port1 ls1-port2
ovn-nbctl list address_set

Creating a port group automatically creates two address sets that OVN keeps in sync as members change:

ReferenceExpands toUse in a match
@pg-webThe member portsoutport == @pg-web

This is exactly how a Neutron remote security group rule stays correct forever: the rule names the group, not the addresses, so adding a VM rewrites the address set rather than the ACL.

Stateful ACLs

ovn-nbctl acl-add pg-web to-lport 1000 'outport == @pg-web && ip4 && tcp.dst == 80' allow-related
ovn-nbctl acl-add pg-web from-lport 1001 'inport == @pg-web && ip4' allow-related

DIRECTION

Direction is expressed from the logical switch’s point of view. from-lport is traffic leaving the VM (Neutron egress); to-lport is traffic arriving at the VM (Neutron ingress). The inport/outport in your match must agree with the direction or the ACL will never fire.

DEFAULT DROP

As soon as any ACL exists on a switch or port group, OVN installs an implicit low-priority drop for that datapath. That is why a Neutron port with a security group attached is closed by default — and why removing all rules is not the same as removing the group.

Exposing the databases

A single-node lab talks to the OVN databases over a Unix socket. As soon as a second chassis exists, the Southbound DB must be reachable over the network.

ovn-nbctl set-connection ptcp:6641:0.0.0.0
ovn-sbctl set-connection ptcp:6642:0.0.0.0
ovn-nbctl set Connection . inactivity_probe=60000
ovn-sbctl set Connection . inactivity_probe=60000
INACTIVITY PROBE

The default probe interval is 5 s. On a laptop-hosted lab a brief stall makes ovn-controller think central died and reconnect in a loop. Raising it to 60 s removes that noise. Production deployments tune this too — and use SSL rather than plain TCP.

Registering a chassis

Each chassis advertises three things through the local OVS database. ovn-controller reads them at start-up, connects to the Southbound DB, and creates its Chassis row.

ovs-vsctl set open . \
  external-ids:ovn-remote=tcp:$CENTRAL_IP:6642 \
  external-ids:ovn-encap-type=geneve \
  external-ids:ovn-encap-ip=$NODE2_IP
ovn-sbctl show
external-idMeaning
ovn-remoteWhere the Southbound DB lives
ovn-encap-typeOverlay protocol — geneve for OVN
ovn-encap-ipThis node’s underlay IP; peers build tunnels to it
system-idChassis name shown by ovn-sbctl show

Binding a port across hosts

Port binding is the moment a logical port becomes physical. The chassis whose OVS interface carries external-ids:iface-id claims the port in the Southbound DB, and every other chassis learns to tunnel to it.

ovs-vsctl add-port br-int veth-b-ovs
ovs-vsctl set interface veth-b-ovs external-ids:iface-id=ls1-port2
ovn-sbctl list Port_Binding ls1-port2

Concepts

A chassis is a hypervisor

Nothing about a chassis is special beyond ovn-controller, an integration bridge, and three external-ids. Add the row, and the rest of the fabric adapts. This is why adding a compute node to OpenStack is a package install plus configuration, not a topology change.

The tunnel mesh is automatic

You never create a Geneve tunnel in OVN. When a chassis registers with an ovn-encap-ip, every other ovn-controller sees the new Chassis row and adds a port to the genev_sys_6081 mesh. Remove the chassis and the tunnels disappear.

ovs-vsctl show | grep -A3 geneve
ovs-appctl bfd/show

East/west routing is distributed (DVR)

A logical router is not a device on a node. Its flows are installed on every chassis, so a packet from ns-a to a VM on another subnet is routed by the source hypervisor and then tunnelled straight to the destination hypervisor. There is no hairpin through a network node.

North/south is centralized on a cr-lrp

SNAT is stateful, and conntrack state cannot be replicated across every hypervisor. So the router port that faces the external network gets a chassisredirect port — cr-lrp — pinned to a single chassis. Traffic that needs SNAT is tunnelled to that chassis first.

ovn-sbctl show | grep cr-
ovn-sbctl list Port_Binding | grep -A5 chassisredirect

Gateway HA

Pinning to one chassis is a single point of failure, so OVN lets you nominate several candidates with priorities. The highest-priority reachable candidate wins; liveness comes from BFD over the Geneve tunnels, so failover is sub-second rather than a timeout.

ovn-nbctl lrp-set-gateway-chassis lr1-ext node1 100
ovn-nbctl lrp-set-gateway-chassis lr1-ext node2 50
ovn-nbctl lrp-get-gateway-chassis lr1-ext

This is precisely OpenStack’s L3 HA for ML2/OVN — and max_gw_chassis in neutron.conf caps the candidate list.

Multi-node setup

Every lab here runs on a single host. To extend to a multi-node setup:

  • Two or more Linux hosts with IP reachability between them.
  • One host runs ovn-central (NB DB, SB DB, ovn-northd).
  • Every host runs ovs-vswitchd, ovsdb-server, and ovn-controller.

Per-chassis configuration:

apt install -y openvswitch-switch ovn-host
ovs-vsctl set open . \
  external-ids:ovn-remote=tcp:<central-ip>:6642 \
  external-ids:ovn-encap-type=geneve \
  external-ids:ovn-encap-ip=<this-host-tunnel-ip> \
  external-ids:system-id=<unique-hostname>

On the central host, expose the SB and NB databases on the network:

ovn-sbctl set-connection ptcp:6642
ovn-nbctl set-connection ptcp:6641

Once each ovn-controller connects, Geneve tunnels appear automatically on br-int. Verify with ovs-vsctl show and ovn-sbctl show.
