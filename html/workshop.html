OpenStack Networking Workshop

Build a complete OpenStack-style virtual network from first principles — namespaces, veth pairs, Open vSwitch, OpenFlow, and finally OVN.

This workshop walks you, hands-on, through the same data-plane primitives OpenStack Neutron uses under the hood. Five labs, roughly 6.5 hours end to end, no real cloud required — everything can be done in the embedded mock lab environment.

The five labs

Lab 1 · ~45 minTAP devices & namespaces

Isolation primitives: virtual NICs and per-process network stacks.

 Lab 2 · ~45 minVeth pairs

Connect two namespaces and watch ARP fly across the wire.

 Lab 3 · ~1 hrOVS as an L2 switch

Three namespaces, one virtual switch, MAC learning in action.

 Lab 4 · ~1.5 hrOpenFlow rules & tunnels

Program OVS by hand. Drop traffic with a flow. Meet VXLAN and Geneve.

 Lab 5 · ~2.5 hrOVN basics

Logical switches, routers, ACLs, native DHCP. Map it all to Neutron.

What you will learn

  • How Linux network namespaces, veth pairs, and TAP devices isolate and connect virtual NICs.
  • How Open vSwitch differs from a Linux bridge, and why OVN sits on top of OVS.
  • How OpenFlow rules are matched, prioritised, and chained across tables.
  • How VXLAN encapsulates Layer 2 over a routed underlay — and why OVN prefers Geneve.
  • How every OVN concept (logical switch, router, ACL, DHCP options) maps onto Neutron CLI calls.

Recommended path

  1. Read Getting started for prerequisites and environment options.
  2. Skim the Lab environment page to learn the embedded terminal.
  3. Work through Labs 1–5 in order — each builds on the previous.
  4. Keep the Command reference open in another tab.

Workshop›Getting started

Getting started

This workshop is hands-on. You will run ip netns, ovs-vsctl, ovn-nbctl and friends. You can do that in three different environments — pick whichever suits you.

Prerequisites

  • Comfort with the Linux command line.
  • Basic networking: IP addresses, subnets, MAC addresses, ARP, ICMP.
  • For the real-host options: a recent Ubuntu (22.04 or newer) and sudo rights.

Option 1: The mock lab environment (recommended)

The fastest way to start. Every lab page embeds an interactive terminal that simulates the commands you would run on a real host. No VM, no installs, no risk of breaking your laptop.

Open any lab and start typing. The terminal seeds the state from the previous lab so you can pick up where you left off.

Best for

Reading and learning — you can complete every exercise this way.

Option 2: A single Linux VM

If you want the real thing, the simplest setup is a single Ubuntu VM with everything installed locally:

apt update
apt install -y iproute2 openvswitch-switch ovn-central ovn-host tcpdump

Every command in every lab works on this single host. The chassis IP and tunnel endpoint are simply 127.0.0.1.

Option 3: A multi-node setup

For the full distributed experience — Geneve tunnels between real chassis — you need two or more Linux hosts. See the Reference, section Multi-node setup guidance, for the broad strokes.

Privileges and cleanup

Every command in this workshop requires root or sudo. The mock environment runs as root. On real hosts, prefix with sudo.

Each lab ends with a cleanup step. If you skip it you can always wipe namespaces and the bridge by hand:

for ns in $(ip netns list | awk '{print $1}'); do ip netns del $ns; done
ovs-vsctl del-br br-int 2>/dev/null || true

Workshop›Fundamentals›Lab 1

Lab 1 — TAP devices & namespaces

Tier
Fundamentals
Duration
~45 minutes
Prerequisites
Comfort with the Linux CLI and basic networking.

Objectives

  • Understand what a network namespace is and why OpenStack uses them.
  • Create, list and delete namespaces.
  • Create a TAP device and place it inside a namespace.
  • Verify isolation: namespaces have independent interfaces, addresses and routes.

Background

A network namespace gives a process its own private network stack: its own interfaces, its own ARP table, its own routes. Two namespaces cannot see each other’s traffic unless you explicitly connect them. This is the same isolation primitive containers use.

A TAP device is a virtual Layer 2 NIC. The kernel treats it as a real Ethernet interface; a userspace program (or, in OpenStack, QEMU) can read and write Ethernet frames through it. Every VM in OpenStack has a TAP device on the hypervisor.

Try it

Exercises

Exercise 1 — List existing namespaces

ip netns list

Verify:

  • On a fresh host the list is empty.

Exercise 2 — Create two namespaces

ip netns add ns-a
ip netns add ns-b
ip netns list

Verify:

  • ns-a and ns-b appear in the list.

Exercise 3 — Inspect a namespace

ip netns exec ns-a ip link show
ip netns exec ns-a ip addr show

Questions:

  • What interfaces exist inside ns-a by default?
  • Is the loopback (lo) up or down?

Exercise 4 — Bring up loopback inside a namespace

ip netns exec ns-a ip link set lo up
ip netns exec ns-a ping -c2 127.0.0.1

Exercise 5 — Create a TAP device

ip tuntap add dev tap-a mode tap
ip link show tap-a

Verify:

  • The TAP device exists in the root namespace.

Exercise 6 — Clean up

ip link del tap-a
ip netns del ns-a
ip netns del ns-b

Review questions

  1. What kernel feature makes namespaces possible?
  2. Why does OpenStack put each router into its own network namespace (in legacy ML2)?
  3. How does a TAP device differ from a veth?
  4. If two namespaces both have an interface eth0, do they conflict?

Lab 2 — Veth pairs

Tier
Fundamentals
Duration
~45 minutes
Prerequisites
Lab 1 completed.

Objectives

  • Explain what a veth pair is and how it differs from a TAP device.
  • Create a veth pair connecting two namespaces.
  • Assign IPs, ping across the pair, and observe ARP.

Background

A veth pair is a kernel construct: two virtual Ethernet interfaces wired together back-to-back. Whatever you transmit on one end appears on the other. They are the standard way to connect a namespace (or container) to another namespace or to a bridge.

PropertyTAPveth pair
EndpointsOne (userspace fd on the other side)Two interfaces, two ends
Typical useVM NIC (QEMU)Connect namespaces and bridges
Created withip tuntap addip link add type veth

Try it

Exercises

Exercise 1 — Create two namespaces

ip netns add ns-a
ip netns add ns-b

Exercise 2 — Create a veth pair

ip link add veth-a type veth peer name veth-b
ip link show | grep veth

Exercise 3 — Move each end into its namespace

ip link set veth-a netns ns-a
ip link set veth-b netns ns-b

Verify:

  • ip link show in the root namespace no longer shows veth-a or veth-b.
  • ip netns exec ns-a ip link show shows veth-a.

Exercise 4 — Bring interfaces up

ip netns exec ns-a ip link set lo up
ip netns exec ns-a ip link set veth-a up
ip netns exec ns-b ip link set lo up
ip netns exec ns-b ip link set veth-b up

Exercise 5 — Assign IPs

ip netns exec ns-a ip addr add 10.0.0.1/24 dev veth-a
ip netns exec ns-b ip addr add 10.0.0.2/24 dev veth-b

Exercise 6 — Ping across

ip netns exec ns-a ping -c3 10.0.0.2

Verify:

  • Pings succeed; the namespaces are now connected at Layer 2.

Exercise 7 — Observe ARP

ip netns exec ns-a ip neigh show
ip netns exec ns-b ip neigh show

Questions:

  • Whose MAC appears in each neighbour table?
  • What happens if you delete the entry and ping again?

Exercise 8 — Clean up

ip netns del ns-a
ip netns del ns-b
Tip

Deleting a namespace also removes any veth ends it holds. The peer end goes away with it.

Review questions

  1. Why does a veth always come as a pair?
  2. What happens to the peer if you delete one end of a veth?
  3. In OpenStack, where would you typically find veth pairs?

Lab 3 — OVS as an L2 switch

Tier
Open vSwitch
Duration
~1 hour
Prerequisites
Labs 1 and 2 completed.

Objectives

  • Explain why OpenStack uses OVS rather than the Linux bridge.
  • Create an OVS bridge and connect three namespaces through it.
  • Inspect the default flow table and observe MAC learning.

Why a virtual switch?

In Lab 2 you connected two namespaces with one veth pair. For three or more, a full mesh scales as O(N²). A switch reduces that to O(N): each namespace gets one veth, the other end plugs into the switch.

Full mesh (3 namespaces): Star via switch: ns-a ──── ns-b ns-a ─┐ \ / ns-b ─┼── br-int (OVS) ns-c ns-c ─┘ (3 pairs, O(N²)) (3 pairs, O(N))

Why OVS, not the Linux bridge?

FeatureLinux bridgeOVS
MAC learningYesYes
Programmable flow rulesNoYes
OpenFlow controllerNoYes
VXLAN / Geneve tunnelsNoYes
Used by OVNNoYes

Try it

Exercises

Naming

For each namespace ns-X, create a veth pair with two ends: veth-X (inside the namespace) and veth-X-ovs (in the host, plugged into br-int).

Exercise 1 — Install OVS

apt install -y openvswitch-switch

In the mock environment, OVS is pre-installed.

Verify:

  • ovs-vsctl show returns an empty configuration with a version.

Exercise 2 — Create an OVS bridge

ovs-vsctl add-br br-int
ip link set br-int up

Verify:

  • ovs-vsctl show — br-int is present.
  • ovs-ofctl dump-flows br-int — what flows exist by default?

Exercise 3 — Connect three namespaces

For each of ns-a, ns-b, ns-c:

  1. Create the namespace.
  2. Create a veth pair veth-X / veth-X-ovs.
  3. Move veth-X into the namespace.
  4. Add veth-X-ovs to br-int.
  5. Bring everything up.

Exercise 4 — Assign IPs

  • ns-a: 192.168.100.10/24
  • ns-b: 192.168.100.20/24
  • ns-c: 192.168.100.30/24

Exercise 5 — Verify connectivity

Ping between every pair. All should succeed thanks to the default NORMAL flow.

Exercise 6 — Inspect OVS state

ovs-vsctl show
ovs-ofctl dump-flows br-int
ovs-ofctl dump-ports br-int
ovs-appctl fdb/show br-int

Questions:

  • How many flows are installed by default?
  • After pinging, what MACs appear in the FDB?
  • What does n_packets in dump-flows tell you?

Exercise 7 — Observe ARP and broadcast

Capture on all three veth-X-ovs ports, clear the ARP cache in ns-a, then ping ns-b.

Questions:

  • Does the ARP request appear on veth-c-ovs? Why?
  • Does the reply appear there? Why or why not?

Exercise 8 — Clean up

ovs-vsctl del-br br-int
ip netns del ns-a; ip netns del ns-b; ip netns del ns-c

Review questions

  1. What does the default NORMAL action do?
  2. Why does OVN use OVS instead of the Linux bridge?
  3. What happens when a frame arrives at OVS with an unknown destination MAC?

Lab 4 — OpenFlow rules & tunnels

Tier
Open vSwitch
Duration
~1.5 hours
Prerequisites
Labs 1–3 completed.

Objectives

  • Understand match, priority, and actions in an OpenFlow rule.
  • Add and remove flows with ovs-ofctl.
  • Implement an ACL by dropping traffic.
  • Explain VXLAN encapsulation and why OVN prefers Geneve.

OpenFlow basics

A flow rule has three parts: match (in_port, MAC, IP, ports, …), priority (0–65535, higher wins), and actions (output:<port>, drop, resubmit(,N), NORMAL, …).

Incoming packet │ ▼ ┌─ Table 0 ──────────────────────────────────────────┐ │ priority=200, ip, nw_src=10.0.0.1 → actions=drop │ │ priority=100, ip → actions=NORMAL│ │ priority=0 → actions=NORMAL│ └────────────────────────────────────────────────────┘

First match by descending priority wins.

VXLAN & Geneve

VXLAN encapsulates Ethernet frames inside UDP (port 4789). Each tunnel carries a 24-bit VNI (~16M values). OVN uses Geneve instead, because Geneve’s TLV headers can carry OVN’s logical datapath and port metadata.

PropertyVXLANGeneve
HeaderFixedExtensible TLVs
OVN metadataNot supportedCarries datapath + port IDs
RFC73488926

Exercises

Exercise 1 — Default flow and port counters

ovs-ofctl add-flow br-int \

  • Ping from ns-c to ns-b still works.

Exercise 3 — Remove the ACL

ovs-ofctl del-flows br-int \

Exercise 4 — Port-based match

Drop frames ingressing veth-a-ovs with a specific destination MAC. ARP (broadcast) still works; ICMP is blocked.

Exercise 5 — Statistics

  • Difference between ovs-ofctl dump-flows and ovs-dpctl dump-flows?

Lab 5 — OVN basics

Tier
OVN
Duration
~2.5 hours
Prerequisites
Labs 1–4 completed.

Objectives

  • Explain OVN’s architecture and its relationship to OVS.
  • Create logical switches, ports, and routers.
  • Bind logical ports to OVS interfaces.
  • Implement ACLs and OVN-native DHCP.
  • Map every OVN concept to its OpenStack Neutron equivalent.

Why OVN?

Programming OVS by hand works for a few ports. For a real cloud with thousands of VMs you need automation. OVN takes high-level intent (“create a network”), compiles it into logical flows, distributes them, and lets each chassis’ ovn-controller compile them into local OpenFlow rules.

Architecture

┌───────────────────────────┐ │ Northbound DB │ ← Logical topology │ (networks, routers, ACLs)│ (Neutron writes here) └─────────────┬─────────────┘ │ ┌─────────────▼─────────────┐ │ ovn-northd │ ← Compiles NB → SB └─────────────┬─────────────┘ │ ┌─────────────▼─────────────┐ │ Southbound DB │ ← Logical flows + │ (logical flows, chassis) │ chassis bindings └──────┬─────────────┬──────┘ │ │ ┌─────────▼──┐ ┌─────▼───────┐ │ovn-controller ovn-controller│ │ (Host A) │ │ (Host B) │ └──────┬─────┘ └──────┬──────┘ │ │ ┌──────▼─────┐ ┌──────▼─────┐ │ br-int │ │ br-int │ └────────────┘ └────────────┘

Create DHCP options for 10.0.1.0/24, attach them to the ports, run dhclient inside a namespace. No dnsmasq involved — DHCP is served by OVS flows.

Multi-node setup

Every lab here runs on a single host. To extend to a multi-node setup:

  • Two or more Linux hosts with IP reachability between them.
  • One host runs ovn-central (NB DB, SB DB, ovn-northd).
  • Every host runs ovs-vswitchd, ovsdb-server, and ovn-controller.

Per-chassis configuration:

apt install -y openvswitch-switch ovn-host
ovs-vsctl set open . \
  external-ids:ovn-remote=tcp:<central-ip>:6642 \
  external-ids:ovn-encap-type=geneve \
  external-ids:ovn-encap-ip=<this-host-tunnel-ip> \
  external-ids:system-id=<unique-hostname>

On the central host, expose the SB and NB databases on the network:

ovn-sbctl set-connection ptcp:6642
ovn-nbctl set-connection ptcp:6641

Once each ovn-controller connects, Geneve tunnels appear automatically on br-int. Verify with ovs-vsctl show and ovn-sbctl show.
